# Payment Reference Code System

## Overview

EduPulse currently operates with a mixed reference system:

- legacy compact payment codes generated from `backend/utils.py`
- structured fee references generated directly by the payment-instruction service for newer workflows such as feeding plans and tuition installments

This is intentional. The platform preserves backward compatibility for already-deployed compact references while using clearer structured references where the new product flow needs richer categorization.

## Current Reference Families

### Legacy compact codes

Generated by `generate_all_payment_codes(student_id, fees_config)`.

Examples:

- `CFK011` for non-installment tuition
- `CFK012` for legacy feeding fallback
- `CFK013` for uniform
- `CFK014` for transport

Custom fees continue from the next numeric suffix.

### Structured references

Generated by the payment-instruction layer for specific workflows.

Current active examples:

- `S001-TUIT-I1` for tuition installment 1
- `S001-TUIT-I2` for tuition installment 2
- `S001-FEED-DAY` for daily feeding
- `S001-FEED-WEK` for weekly feeding
- `S001-FEED-MON` for monthly feeding

## Why The System Is Mixed

EduPulse needed to add:

- installment-specific tuition routes
- feeding-plan-specific references
- exact tracked transfer routing per fee path

without breaking schools already using the older compact reference scheme.

The result is:

- compact references remain valid and parseable
- structured references are preferred for newer fee families that need human-readable suffixes or installment metadata

## Where Each Format Appears

### Student payment instructions

The payment-code payload returned by `GET /api/students/<student_id>/payment-codes` can now include both styles at the same time.

Examples:

- tuition installment references such as `S001-TUIT-I1`
- feeding references such as `S001-FEED-MON`
- compact references for uniform, transport, or classic tuition routes

### Manual receive-payment flow

`POST /api/finance/receive-payment` can still resolve supported references into a learner and fee type.

### Automatic tracked transfer flow

When a Paystack tracked transfer account is prepared for a fee route, the stored `PaymentCollectionIntent` binds that route to the learner and fee purpose. In that mode, the visible reference remains useful for support and manual follow-up, but Paystack route matching is the primary automation path.

## Tuition Installment Behavior

When installments are enabled in Settings:

- the school chooses `2`, `3`, or a custom installment count
- EduPulse can auto-split the tuition evenly
- each installment can be edited before save
- the final saved amounts must add up exactly to the tuition fee
- each installment gets its own dedicated reference and virtual account route
- statuses can move through `upcoming`, `open`, `partial`, `paid`, and `overdue`
- small overpayments can carry forward into the next installment as credit

## Tracked Transfer Behavior

For tuition tracking, the recommended workflow is now:

1. Generate or print the learner's payment instructions
2. Let EduPulse create or reuse the Paystack tracked transfer account
3. Share the exact amount, bank name, account number, and preferred reference with the parent
4. Let Paystack `charge.success` trigger the automatic recording path

If automatic tracking fails because of a missed provider event or a temporary integration issue, EduPulse also exposes a reconciliation fallback through `POST /api/finance/paystack/recover-reference`.

## Example API Payload

```json
{
  "payment_codes": [
    {
      "fee_type": "Tuition",
      "reference_code": "S001-TUIT-I1",
      "base_amount": 500.0,
      "total_amount": 509.75
    },
    {
      "fee_type": "Uniform",
      "reference_code": "CFK013",
      "base_amount": 300.0
    }
  ]
}
```

## Operational Rule

Do not assume every EduPulse fee reference is now fully human-readable. The current platform emits:

- readable structured references where the newer logic needs them
- compact references where older fee-code generation is still the active behavior

Both are valid in the current system.

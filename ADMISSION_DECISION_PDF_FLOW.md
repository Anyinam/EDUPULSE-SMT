# Admission Decision PDF Flow

## Purpose

This document defines the recommended admission-decision PDF workflow for EduPulse.

It is a design specification, not a statement that the feature is already implemented.

The design follows three rules:
- the school remains the approval authority
- document delivery must stay school-controlled
- rejection should not automatically generate an admission letter PDF or any other PDF unless the school explicitly chooses to support that later

## Product Rule

Default behavior:
- `Approved`: school may choose to issue an admission decision PDF
- `NeedsCorrection`: no admission letter PDF by default
- `Rejected`: no PDF by default
- `VisitRequired` or `TestReady`: no admission letter PDF by default

This keeps the product from sending the wrong kind of document for a negative or incomplete decision.

## Recommended Scope

### 1. Approval Document

Recommended document name:
- Admission Decision PDF
- or Admission Offer Letter PDF

Recommended use:
- generated only after school approval
- generated only if the school has enabled approval-PDF delivery in settings

Recommended contents:
- school branding
- learner full name
- application code
- admission decision date
- class offered
- reporting date or next-step date if provided by the school
- school-specific items needed after approval
- payment summary or payment-link reference when relevant
- contact instructions for questions
- authorized school sign-off block

Recommended exclusions:
- do not expose internal AI scoring details
- do not expose raw internal reviewer metadata
- do not expose internal staff IDs or audit details

### 2. Correction Request

Default recommendation:
- use the parent status page and review notes as the main correction surface
- show missing items and required uploads directly in the portal
- do not auto-generate a PDF unless the school explicitly enables a checklist-style document later

Reasoning:
- correction requests are iterative and change often
- a live status page is better than a static PDF for incomplete applications

Future optional variant:
- school-configurable Correction Checklist PDF
- disabled by default

### 3. Rejection Decision

Default recommendation:
- do not generate any rejection PDF automatically
- show the outcome on the parent status page
- send text/email feedback if school policy allows

Reasoning:
- many schools will not want formal rejection letters automatically issued
- some schools may prefer no written rejection document at all
- others may want a manually reviewed policy-driven notice

Future optional variant:
- school-uploaded rejection notice template
- disabled by default
- must be explicitly enabled by the school

## Delivery Channels

Recommended delivery order for approved applications:
1. Parent status page updates immediately
2. Parent receives admission-update email if email is available
3. Status page exposes a PDF download button if the school enabled approval PDFs
4. Email may include either:
   - a secure download link
   - or the PDF as an attachment if delivery limits and policy allow

Recommended default for correction and rejection:
- status page first
- email text update second
- no automatic PDF

## School Controls

Recommended settings:
- `approval_pdf_enabled`
- `approval_pdf_delivery_mode`
- `approval_pdf_include_payment_summary`
- `approval_pdf_include_required_items`
- `correction_pdf_enabled` default `false`
- `rejection_pdf_enabled` default `false`

Recommended delivery-mode options:
- `status_page_only`
- `email_link`
- `email_attachment`

Recommended policy behavior:
- if `approval_pdf_enabled` is `false`, approved parents still see the decision on the status page and by email, but no PDF is generated
- if `rejection_pdf_enabled` is `false`, no rejection PDF is ever generated
- if `correction_pdf_enabled` is `false`, correction remains portal-first

## Recommended Backend Flow

### Approval Path

1. School reviews application and chooses `approve`
2. Student admission record is created
3. Parent status page updates to `Approved`
4. If school setting `approval_pdf_enabled` is true:
   - build admission decision payload
   - render PDF
   - store document metadata
   - attach secure document reference to the parent-facing status payload
5. Send parent email update
6. If configured, include PDF link or attachment

### Correction Path

1. School reviews application and chooses `request_correction`
2. Parent status page updates to `NeedsCorrection`
3. Reviewer notes and missing items appear on the status page
4. No PDF is generated by default
5. Parent resubmits updates through the correction flow

### Rejection Path

1. School reviews application and chooses `reject`
2. Parent status page updates to `Rejected`
3. Reviewer notes appear if school policy allows them
4. No PDF is generated by default
5. Parent email update may be sent, but without an attachment by default

## Parent Experience

### Approved
- status page shows approval state
- payment path appears if relevant
- PDF download appears only if the school enabled approval PDFs
- the document can include the list of things needed after approval

### NeedsCorrection
- status page shows what is missing
- parent updates details and uploads the missing files
- no static PDF is necessary in the default flow

### Rejected
- status page shows final outcome
- no rejection PDF is shown unless the school explicitly enables such a workflow in the future

## Recommended Data Model Additions

If implemented later, the cleanest additions are:
- school-level PDF policy settings
- optional document template settings for approval, correction, and rejection
- admission-decision document record linked to the application
- secure parent-facing document URL with access control

Suggested metadata fields:
- `document_type`
- `application_id`
- `school_id`
- `status_generated_for`
- `generated_at`
- `delivery_mode`
- `file_path` or object-storage key
- `is_parent_visible`

## Commercial Fit

This feature should align with the AI Employee packaging strategy:
- approval-document generation should ride inside the bundled AI Registrar capability for paid subscription schools
- correction and rejection PDFs should remain optional policy controls, not assumed defaults
- communications channel costs should still be separated from AI workflow pricing

## Final Recommendation

Recommended first implementation order:
1. approval-only admission decision PDF
2. school setting to enable or disable approval PDF generation
3. status-page download plus email-link delivery
4. school-managed required-items section inside the approval PDF
5. keep correction and rejection PDF generation disabled by default

This gives schools a usable approval document without forcing formal PDFs into decisions where many schools will want discretion.
